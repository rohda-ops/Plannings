### Phase 1 — Ingestion generates the agent (starting point)

- The procedure document is the input — this is the human-written playbook describing what needs to be checked and how.
- The ingestion pipeline reads that document and produces an agent. This agent is not code with a database connection — it's a specification: a question to answer, plus reasoning instructions for how to think through the answer once it has data in front of it.
- At this point nothing has run yet. It's just written instructions sitting there, unproven.

### Phase 2 — db_discovery builds the way to get real data

- Separately, db_discovery looks at the same procedure document and also looks at the real database schema.
- Using Graph RAG, it explores the relationships between tables and columns and finds the ones that most likely correspond to the terms used in the procedure document.
- From that, it builds an actual query — something that can run against the real database and pull back real values.
- This query, when executed, is what supplies the data that ingestion's agent will later reason over. Without this step, the ingestion agent has nothing to look at.

### Phase 3 — Running the pair together (test execution)

- For a given test case, db_discovery's query runs against a safe test copy of the database and returns real data.
- That data is handed to the ingestion-generated agent's reasoning instructions.
- The agent reasons over that real data and produces a final answer.
- This is the only point where anything actually executes — everything before this was just document-reading and instruction-writing.

### Phase 4 — Comparing against the old manual answers

- Long before any of this automation existed, humans manually worked through these same kinds of questions and wrote down answers. Those old answers are the ground truth — not generated by any of these pipelines, not something GEPA or db_discovery produced.
- GEPA takes the final answer produced in Phase 3 and checks it against the matching old manual answer for that same case.
- Where they match, that case is currently working. Where they don't match, that's a confirmed miss — something in the chain broke, and now there's a concrete, correct answer to compare against.

### Phase 5 — GEPA figures out where in the chain it broke

- For every miss, GEPA doesn't just see "wrong" — it looks at everything that happened along the way: which columns db_discovery's Graph RAG considered and picked, the query it built, the data that actually came back, and the reasoning the ingestion agent applied to that data.
- By looking at this full trail alongside the correct manual answer, GEPA can usually tell whether the problem happened earlier (wrong columns were found, or the query pulled the wrong data) or later (the right data came back, but the reasoning drew the wrong conclusion from it).
- This distinction matters because the fix is different depending on where it broke — fixing db_discovery's column-finding logic doesn't help if the real problem is in how ingestion reasons over correct data, and vice versa.

### Phase 6 — GEPA rewrites the responsible instructions

- Once GEPA has a sense of where the failure happened, it rewrites the instructions for that specific part — either db_discovery's logic for choosing columns and building the query, or ingestion's reasoning instructions, or both if both were implicated.
- It doesn't touch the parts that were working fine. It targets the fix at the piece that actually caused the miss.

### Phase 7 — Test again, keep what's better

- With the rewritten instructions in place, the same test cases (plus a separate set that was held back and never used for fixing, just for double-checking) get run again.
- If the new version answers more cases correctly than the old version, it's kept. If not, GEPA tries a different rewrite.
- This isn't a one-shot fix — it repeats many times, each round nudging the instructions a bit further based on whatever mistakes are still showing up.

### Phase 8 — A human checks before anything becomes the new default

- Before the improved instructions actually replace the current ones in production use, someone on your team reviews what changed and confirms the accuracy improvement is real, not a fluke from a small test set.
- Only after that approval does the new version become the one ingestion and db_discovery actually use going forward.

### The loop, once fully set up

Once Phases 1 through 8 are wired together, this isn't a one-time project — it's something you can re-run any time: new procedure documents come in, more old manual answers get added to the comparison set, or accuracy on a particular type of question is still weak. Each re-run should push accuracy a bit higher than the last, because it's always learning from confirmed real mistakes, not guesses.
